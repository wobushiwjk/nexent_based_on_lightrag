# 工业设备故障诊断与本体治理项目成果说明

更新时间：2026-11-15

## 一、项目是什么

本项目以 Nexent 作为用户唯一入口，基于 LightRAG 构建了一个面向工业设备
维护场景的多智能体诊断与本体治理系统。系统能够从设备手册、维修记录、
巡检表、标准文件和图片中抽取结构化知识，并对故障原因给出可逐字追溯的
证据、故障树位置和人工复核结论。

项目重点解决四类问题：

1. 维修资料分散在 PDF、表格、图片和工单中，检索和交叉判断困难；
2. 通用大模型容易给出没有原文依据、无法审计的诊断结论；
3. 企业本体和故障树需要持续更新，但不能由模型直接修改和发布；
4. 工业现场关注数据隐私和部署成本，不适合完全依赖外部大模型。

## 二、用户最终看到什么

用户不需要了解 MCP、图谱或模型细节，只需要使用 Nexent 对话界面。

### 1. 上传设备资料并直接提问

用户可以在 Nexent 中上传 PDF、CSV、XLSX、PNG/JPEG、Markdown 或 TXT。

随后直接询问：

> 我已上传这份 P-101A 巡检记录，请识别并导入，然后告诉我新增了哪些故障和证据。

系统会完成文件解析、结构化抽取、本体校验、证据校验和知识快照更新。
用户可以在同一个对话中继续查询，无需重启领域服务。

### 2. 给出带证据的故障诊断

示例问题：

> P-101A 冷却水泵出口压力不足，可能的原因有哪些？请逐条给出逐字证据、
> 故障树位置和仍需补充的证据。

系统输出包括：

- 按证据完整度排序的候选故障；
- 每条原因对应的逐字原文；
- 来源文件、页码、表格行或章节；
- 故障树路径和 AND/OR 分支；
- 哪些结论证据完整、哪些仍需验证；
- 下一步排查建议。

系统不会把“可能原因”直接写成“已确认故障”。没有足够证据时，会明确返回
证据缺口，而不是用常识补全。

### 3. 自动进行多智能体复核

复杂诊断或本体变更会调用两个职责独立的子 Agent：

- 证据复核 Agent：检查 quote 是否逐字、来源是否存在、关系方向是否正确、
  故障树是否缺少中间事件；
- 本体专家 Agent：检查类、关系、约束、冲突、Schema 和迁移影响。

主 Agent 负责最终答复。子 Agent 只能复核和建议，不能批准、发布或回滚。

### 4. 从标准文件生成本体变更草案

用户可以上传标准或提交标准节选，要求系统生成新版本本体草案。系统会：

- 保留标准原文和逐字引文；
- 生成类、关系、约束或 gap 变更；
- 检查版本冲突和重复定义；
- 输出机器可读 diff；
- 分析受影响租户、实体、规则、故障树和 Schema；
- 在人工明确批准前保持 `draft` 状态。

### 5. 审核、发布和回滚本体

系统提供完整治理闭环：

```text
draft
→ under_review
→ approved / rejected
→ migrated
→ published
→ rolled_back
```

发布前必须执行迁移 dry-run。发布后生成版本化 JSON Schema，并原子切换
租户活动快照。回滚只切换指针，不删除新版本和旧版本。

## 四、已经实现的核心功能

### 1. 工业故障知识底座

系统已经形成一套可校验的工业故障领域模型：

- 9 个类；
- 11 条关系；
- 8 条约束；
- 7 份 JSON Schema；
- 对齐 IEC 61025、ISO 14224、IEC 60812、ISO 13374。

知识体系包含设备、故障事件、原因规则、证据、文件资产、逻辑门和故障树。
正式事实和因果关系都需要指向原文证据。

### 2. 证据约束的诊断链路

系统不是简单的“向量检索后让模型回答”，而是：

```text
设备确认
→ 候选故障检索
→ 故障树读取
→ 实体/事实/规则逐条取证
→ quote 哈希与字符区间校验
→ 证据复核 Agent
→ 主 Agent 生成最终答复
```

每个结论可以追溯到：

- `evidence_id`；
- 来源文件；
- 页码或表格行；
- 原文字符区间；
- 逐字 quote 哈希。

### 3. 多模态文件进入同一业务流程

项目已完成 PDF、CSV、XLSX、图片和 Markdown/TXT 的本地解析。解析结果进入
统一的设备、故障、事实、规则、证据和故障树模型，而不是只作为普通知识库
文件。

上传导入功能已经通过独立 MCP 接入 Nexent。用户上传文件后，可以由 Agent
自动识别文件、解析、抽取和导入。

### 4. 领域 MCP 和治理 MCP

系统通过 MCP 向 Agent 暴露受控能力，而不是让模型直接访问数据库。

领域 MCP 提供：

- 本体查询；
- 设备查询；
- 故障检索；
- 故障树查询；
- 证据追溯；
- 故障树校验。

治理 MCP 提供：

- 当前版本和历史版本；
- 变更单和审核时间线；
- 草案创建；
- 影响分析；
- 迁移 dry-run；
- 发布；
- 回滚；
- 租户快照历史。

### 5. 三个确定性 Skill

为避免纯大模型编排不稳定，系统实现了三个确定性 Skill：

- 故障诊断流程；
- 证据核验流程；
- 本体变更草案流程。

Skill 只负责调用工具和执行固定校验规则，不自行编造设备事实或证据。

### 6. 三个 Agent 的职责分离

系统由一个主 Agent 和两个受限子 Agent 组成：

- 主 Agent：负责用户意图、工具编排和最终答复；
- 证据复核 Agent：负责证据完整性、引用一致性和故障树缺失节点；
- 本体专家 Agent：负责本体语义、冲突、Schema 和迁移建议。

子 Agent 的真实调用已经在 Nexent 对话中出现，不是提示词模拟。

### 7. 本体版本化和可回退治理

每次本体发布会创建不可变版本和租户快照，包括：

- ontology version；
- tenant runtime run；
- schema artifact set；
- review event timeline；
- publication record。

发布失败时旧版本继续服务。发布成功后可以读取历史版本。回滚后旧、新租户
快照都保留，便于审计和再次切换。

### 8. 本地小模型结构化抽取

项目使用 Qwen2.5-1.5B-Instruct 进行 QLoRA 微调，将通用 1.5B 模型优化为
工业故障候选抽取器。输入是维修记录、手册片段或表格行，输出是故障实体、
因果关系和逐字证据。

学生模型只负责提出候选，后续仍由确定性程序执行本体约束、证据校验和
故障树投影。

## 五、项目做了哪些关键优化

### 1. 从普通 RAG 升级为“图谱 + 证据 + 故障树”

普通 RAG 往往只返回相似文本片段。本项目的检索结果还包含：

- 设备实体；
- 故障事件；
- 原因规则；
- AND/OR 逻辑门；
- 故障树路径；
- 每条结论对应的原文证据。

在 P-101A 端到端场景中，纯词法检索可以找到故障名称，但证据覆盖率是 0，
也无法生成故障树；完整图谱路径达到：

- 检索命中率 1.0；
- 证据覆盖率 1.0；
- quote 哈希有效率 1.0；
- 字符区间有效率 1.0；
- 故障树结构匹配；
- 原因分支覆盖率 1.0。

### 2. 将证据校验做成硬约束

系统不会直接信任大模型或小模型给出的 quote。只有满足以下条件的内容才能
进入正式知识：

- quote 是输入原文的连续子串；
- quote 哈希一致；
- 字符区间一致；
- 来源资产存在；
- 目标实体、事实或规则存在；
- 关系方向和允许的类型正确。

违规内容进入审核队列，不进入活动知识快照。

### 3. 用任务分工降低大模型不确定性

系统将任务拆成：

```text
模型负责理解和候选抽取
程序负责证据、本体、Schema 和版本校验
Agent 负责编排和解释
人工负责最终审批和发布
```

这种分工避免让单一模型同时承担诊断、审批、发布和审计职责。

### 4. 本地小模型降低部署成本

与通用基座相比，微调后的 B1 学生模型在 652 条固定测试集上实现：

| 指标 | 基座 | 微调后 |
|---|---:|---:|
| JSON 合法率 | 0.9678 | 1.0000 |
| Contract 合法率 | 0.0015 | 0.9801 |
| 实体 F1 | 0.1702 | 0.6841 |
| 关系 F1 | 0.0000 | 0.5212 |
| 逐字证据率 | 0.8136 | 0.9824 |
| 负样本准确率 | 0.0255 | 0.9745 |
| 平均输出 tokens | 337.90 | 92.13 |

主要变化：

- 输出格式和合同约束显著改善；
- 实体、关系和负样本识别显著优于基座；
- 平均输出长度减少约 73%，更适合本地推理；
- 在结构化中文泵手册测试组上，实体 F1 为 0.9845，关系 F1 为 0.9767；
- 在 CFDK 自由维修文本组上，实体 F1 为 0.6325，关系 F1 为 0.1910。

当前模型在结构化中文设备资料上效果突出，在自由维修文本的复杂因果关系
抽取上仍有明显提升空间。项目按数据组分别报告结果，没有把不同场景混在
一起夸大。

### 5. 上传后无需重启服务

领域 MCP 会检测租户活动快照变化并热刷新。用户上传并导入新资料后，可以在
同一个 Nexent 对话中立即检索，不需要每次重启 MCP。

### 6. Nexent 协议兼容

针对模型输出 `<｜DSML｜>` 工具调用格式的问题，项目增加了独立兼容层：

- 支持全角和 ASCII DSML；
- 支持多工具调用；
- 支持参数乱序、单引号和 JSON 参数；
- 在 Nexent 解析前转换成合法动作；
- 不修改已有领域 MCP 和 Skill 的业务逻辑。

## 六、故障诊断效果示例

演示设备：P-101A 冷却水泵。

用户问题：

> 出口压力不足，可能原因有哪些？请给出证据出处，并说明故障树位置。

系统输出：

1. 入口过滤器堵塞，证据较完整；
2. 叶轮汽蚀，仍待现场验证；
3. 故障树路径：

```text
出口压力不足
→ OR
  ├── 入口过滤器堵塞
  └── 叶轮汽蚀
```

系统同时指出：

- 过滤器分支有巡检压差和维修记录；
- 汽蚀分支有手册机理，但缺少振动、噪声或 NPSH 实测；
- 清理过滤器后的压力恢复记录不足时，不能写“已确认”；
- 下一步应清理过滤器、复测出口压力，再决定是否检查汽蚀。

该结果证明系统不是简单列原因，而是能解释证据完整性和验证闭环。

## 八、项目创新点

### 1. 证据门控而不是答案后补引用

证据不是回答完成后由模型“补一个来源”，而是在候选实体、事实、规则和
故障树节点生成阶段就参与校验。

### 2. 知识更新与知识使用分离

领域 MCP 只负责查询和校验；治理 MCP 负责变更；上传 MCP 负责导入。
Agent 不能直接修改存储，模型不能绕过审核发布本体。

### 3. 大模型编排与本地小模型抽取结合

Nexent 主 Agent 负责自然语言理解和任务编排，小模型负责本地结构化抽取，
确定性程序负责证据和本体约束，降低成本和不确定性。

### 4. 可追溯本体演化

每次本体变更都带原文证据、审核事件、Schema 哈希、迁移记录和租户快照。
发布和回滚都是原子操作。

### 5. 面向真实用户而不是脚本演示

文件上传、诊断、证据展示、故障树、审核、发布和回滚都通过 Nexent 对话
入口触发。终端脚本仅用于部署和验收。

## 九、业务价值

- 减少维修工程师在手册、巡检表和维修记录之间反复查找；
- 诊断结果附带可核验的原文证据，便于技术复核；
- 新资料可以通过上传进入既有知识体系；
- 本体和故障树升级有审核、版本和回滚保障；
- 本地小模型更适合数据隐私要求高的工业环境；
- 无法验证的内容采用拒答和降级策略，降低错误确认风险。

## 结语

本项目已经完成从工业资料接入、结构化抽取、图谱与证据构建、故障诊断、
多智能体复核，到本体审核、发布和回滚的完整业务闭环。系统的核心价值不是
“让模型回答得更像专家”，而是让每一条可供用户采用的知识和结论都能追溯
到原文、经过确定性校验，并处于可审核、可版本化和可回滚的治理体系中。
