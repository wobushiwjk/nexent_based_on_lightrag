# 故障诊断报告写作规范

本文件是知识库中的**写作规范**，不是设备事实、不是行业标准原文，不能作为诊断证据引用。诊断证据只能来自 MCP 工具返回的逐字原文。

## 报告结构

一份可复核的故障诊断答复包含五部分，顺序固定：

1. **结论**：最可能的原因，按可能性排序；区分「已确认」与「待验证」。
2. **证据**：每条结论对应的逐字原文与来源。
3. **故障树位置**：该原因在故障树中的路径与逻辑门表达式。
4. **证据缺口**：哪些环节证据不足、需要补充什么记录。
5. **建议的下一步排查**：只写有证据支撑或规程中明确记载的动作。

没有内容的段落可以省略，但不能改变顺序，也不能把「建议」提前到「证据」之前。

## 结论的写法

- 一句话一个结论，不要把多个原因塞进同一句。
- 用「已确认」「部分支持」「待验证」标注证据强度，不要用「肯定」「必然」这类无法由证据支撑的词。
- 故障树上的分支是结构化假设。只有 `trace_evidence` 成功返回证据的分支，才能写成「已确认」。
- 同一现象有多条可能原因时，说明区分它们需要什么额外信息（例如振动频谱、进出口压差、过滤器前后压差）。

## 证据的写法

统一格式：

```
[evidence:<evidence_id>] "逐字原文" —— <来源文件名或 chunk_id>
```

- 引号内逐字复制，不翻译、不改写、不用同义词替换。
- 需要省略时用 `……`，省略前后必须是原文中真实相邻的片段。
- 一份文档支撑多条结论时，每条结论各自引用，不要写「同上」。
- 来源名称使用证据中的 `asset_id` 或 `chunk_id`，方便复核者定位。

## 建议的写法

- 排查动作必须能追溯到证据或知识库中的明确记载（例如维护手册中的处置措施）。
- 涉及安全联锁、带压拆检、带电作业的动作，只指向企业规程和现场工程师确认，不展开步骤。
- 无法给出有依据的建议时，写「建议由现场工程师按规程确认」，不要编造。

## 常见问题

| 问题 | 后果 |
| --- | --- |
| 结论在前、证据后补 | 复核者无法判断结论是否由证据推出 |
| 引号内改写原文 | 证据失去可核对性，等同于编造 |
| 用知识库术语解释替代设备证据 | 术语是定义，不是这台设备发生过什么的证明 |
| 把故障树假设写成已确认原因 | 把结构化猜测当成事实 |
